## 全项目通读分析（只读，未改动代码）

项目代号 G02，ESP32-C3 + ESP-IDF，目标芯片 esp32c3，Flash 8MB，自定义分区表（factory 3M @0x10000 + storage fat 64K）。
源码**全部为 GBK 编码**，读中文注释必须先 `iconv -f GBK -t UTF-8` 转码，否则乱码。

关键结论：
- 版本号 `boardSOFTWARE_VERSION = "AirMonitor_Ver_2_0_0"`，但主体代码库是从**便携式储能电源**（BMS+MPPT+DCAC+SW6303）移植过来的，AirMonitor 的新功能尚未接上。
- 真正跑起来的只有：Print(UART0 115200/Baiku)、Key(GPIO9)、MD_Display(ST7789 SPI + FT6336 触摸 + LVGL9)、MD_HeatManage(未建任务)。
- `boardBMS_IFACE/boardMPPT_IFACE/boardDCAC_IFACE = 0`，`boardEASY_FLASH/boardEASY_LOGGER = 0`（且 CMakeLists 已注释，不编译）。
- `main/board_config.c` 的 `vBoard_StartTask` 中 `bUsb_TaskInit()`、`bHM_TaskInit()`、`vLight_TaskInit()` 被注释。
- Hardware/BSP 四个传感器（ES8311/GXHTC3/QMC5883L/QMI8658C）参与编译但**全项目无任何调用点**，属孤儿代码。
- GPIO 存在冲突隐患：GPIO0 同时是 `gpioASSIST_OPEN_PIN`(推挽输出) 与触摸/传感器 I2C SDA；SW6303 三路的软件 I2C(2/3/4/5/6) 与 LCD SPI(3/4/5/6/2) 完全重叠。
- 架构核心：ComFunc/queue_task.c 的 `Task_T` + lwrb 环形缓冲（3 字节/消息），main/Sys 是「单 FreeRTOS 任务 + 协程式分步状态机」，非多任务并发。
- 上次成功构建：2026-03-11，产物 build/G02.bin 605KB。

## 编码已转 UTF-8 后的二次审查（仍未改动代码）

编码转换验收：226 个 .c/.h 已是 UTF-8 且无 BOM；**仍有 11 个文件是 GBK**（10 个 CMakeLists.txt + `Hardware/Print/DMA_修改说明.txt`）；`Middlewares/EasyFlash/src/ef_env.c` 有 46 处 U+FFFD 乱码残留（该组件不编译，影响小）。
→ 约定更新：源码已可直接用 Read 读取，但 CMakeLists 仍需 iconv 转码。

按 `.agents/skills/embedded-code-review` 规范审查出的真问题（均已逐行验证）：

死机级（潜伏在**已禁用**模块，启用即爆）：
- `Middlewares/Protocol/Modbus/modbus_proto.c:643` `u8 buff[50]` 却 `memcpy(buff, ucpFrameData, 3+ucCharLen)`，ucCharLen 最大 255 → 258 字节写爆 50 字节栈。
- 同文件 `:632` `lwrb_read(..., ucpFrameData, ucCharLen)` 无容量校验 → 堆溢出；`:401` `ucWaitRecLen=ucCharLen+2` 为 u8 会截断；`:497` `memset(&proto[1],0,len-1)`，len=0 时下溢 SIZE_MAX 且 `&proto[1]` 语义错误。
- `Middlewares/Protocol/Baiku/baiku_proto.c:49-54/110-116` malloc 后未判空即 `(*proto)->xxx` 解引用，else 分支还解引用 NULL（双重错误）；`:178` `ucFrameLen` 为 u8 溢出 → `ucaFrameData[-1]` 越界写；`:224` 长度字段无上限校验 → 卡 2s 超时。

活跃路径真会触发：
- `ComFunc/queue_task.c:206` `lwrb_write()` 返回值未检查，队列（仅 16 字节）满时半包写入 → 下次 `us_len%3!=0` → `lwrb_reset` 整队清空并 return -3，控制指令丢失。
- 同文件 `b_result` 声明后从未赋值，now_run 时恒返回 -1，调用方会误判为失败。
- **所有 `taskENTER_CRITICAL()` 都被注释**（queue_task.c / i2c2.c / baiku_proto.c），跨任务入队与软件 I2C 无保护 → 竞态、时序违规。
- `ComFunc/i2c2.c` 的 `ucBuffLen` 从未赋值（全局 0），却用作 VLA 长度且先建数组后校验。

其他：`switch` 缺 default 4 处（自有代码，其中 `print_prot_frame.c:502` 活跃但前置 if 已过滤）；`queue_task.c` 用 malloc 违反项目「严禁运行时动态内存」规范（实为初始化时一次性分配）。

## 修复构建失败：build 缓存残留旧目录名 ESP-C3-3（已解决）

现象：`idf.py build` 时 ninja 先重建 build.ninja → `CMake Error: The source directory ".../ESP-C3-3" does not exist`。
根因：工程目录曾从 `ESP-C3-3` 复制/改名为 `ESP-C3`，build/ 一起搬过来，`build/CMakeCache.txt` 里 `CMAKE_HOME_DIRECTORY`、`G02_SOURCE_DIR`、`SDKCONFIG` 等 9 处仍是旧绝对路径。源码与 `.vscode/settings.json` 无旧路径引用。

处理：删除整个 build/ → 重新 cmake 配置 + 全量编译 → 成功，`build/G02.bin` 605,936 B（与记录一致），`G02.elf` 8.7MB，app 分区余量 81%，bootloader 0x5270 B。

**教训/约定：目录改名或复制工程后，必须删掉 build/ 重建**，不能沿用旧 build（缓存里的绝对路径会失效，且改文本也救不回增量）。

## 本机 ESP-IDF 构建要点（Windows，本机环境）
- 用 PowerShell 跑构建时，`export.ps1` 会被执行策略挡住 → 先 `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force`，再 `. "$env:IDF_PATH\export.ps1"`。
- PATH 里系统 Python 3.14 会干扰，IDF 会去找不存在的 `idf5.5_py3.14_env` → 必须先把 `C:\Espressif\tools\idf-python\3.11.2` 置到 PATH 前，正确的虚拟环境是 `C:\Espressif\python_env\idf5.5_py3.11_env`。
- ninja 默认满并行时曾崩 `0xC0000409`（日志无编译错误）→ 用 `ninja -j 4` 即可编过；再遇同类崩溃可加 `$env:CCACHE_DISABLE='1'`。（PowerShell 工具禁 cmd.exe / Invoke-Expression。）
- 一次可用命令模板：
  `Set-ExecutionPolicy -Scope Process Bypass -Force; $env:PATH="C:\Espressif\tools\idf-python\3.11.2;"+$env:PATH; $env:IDF_PATH='C:\Espressif\frameworks\esp-idf-v5.5.2'; $env:IDF_TARGET='esp32c3'; . "$env:IDF_PATH\export.ps1"; cd <proj>; idf.py build`
