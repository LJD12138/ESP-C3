## 修复：启动即 abort()（newlib/src/locks.c:145）

- 现象：开机打印 `abort() was called at PC 0x403810d3` → `lock_acquire_generic` @ `esp-idf-v5.5.2/components/newlib/src/locks.c:145`，发生在 `uart: queue free spaces: 20`（app_main 里 `uart_driver_install`）之后。
- 定位方法：`riscv32-esp-elf-addr2line -e build/G02.elf 0x403810d3`；用 `nm` 查到 `xIsrStack`=0x3fc92e00(0x600)，而崩溃 SP=0x3fca91a0 不在中断栈内 → 不是真 ISR，是**任务在临界区内**调用 libc。
- 根因：ESP32-C3(RISC-V) 上 `portENTER_CRITICAL` 把中断阈值抬到 EXCM 级，`xPortCanYield()` 返回 false，newlib 锁适配层误判为中断上下文；`vBoard_StartTask()` 用 `mainENTER_CRITICAL()` 包住全部任务创建，DispTask 初始化里的 `ESP_LOGI/ESP_LOGE`、`i2c_driver_install` 日志会调用 printf → `_flockfile(stdout)` → 递归锁 → abort。
- 修复：
  - `main/board_config.c` `vBoard_StartTask()`：`mainENTER_CRITICAL/mainEXIT_CRITICAL` → `vTaskSuspendAll()/xTaskResumeAll()`（挂起调度器，不关中断，允许 printf/malloc）。
  - `main/main.c`：`printf(0, "...")` 参数写错（format=NULL），改为 `printf("...")`（当前 boardSEGGER=0 未编入，属隐患）。
- 已用 ninja 增量编译验证通过（G02.elf / G02.bin 已更新）。
- 遗留隐患：`Hardware/Print/print_iface.c:317/386` 在**任务上下文**调用 `vTaskNotifyGiveFromISR()`，应改为 `xTaskNotifyGive()`。

## 第二轮：vTaskSuspendAll 也不行，改用"临时提优先级"

- 现象（我第一版改成 vTaskSuspendAll 后）：`assert failed: xQueueSemaphoreTake queue.c:1718 (!( xTaskGetSchedulerState() == taskSCHEDULER_SUSPENDED && xTicksToWait != 0 ))`。
- 堆栈：`vBoard_StartTask(board_config.c:212)` → `cDisp_TaskInit(md_display_task.c:76)` → `vDisp_IfaceInit(md_display_iface.c:197)` → `v_print_dma_memory_info(md_display_iface.c:158)` → `ESP_LOGI` → `esp_log_impl_lock_timeout` → `xQueueSemaphoreTake`。
  即 ESP_LOG 的日志锁是**带超时**获取的，调度器挂起期间必然断言。
- 结论：**任务初始化里有 ESP_LOG/printf → 关中断(临界区)会 abort，挂起调度会 assert，两条路都不行**。
- 最终方案：`vBoard_StartTask()` 开头 `uxTaskPriorityGet(NULL)` 保存原优先级 → `vTaskPrioritySet(NULL, startTASK_BOOT_PRIO=10)`（高于 Sys/Disp=4、Key=2、Print/Health=1，低于 configMAX_PRIORITIES=25）→ 创建完再恢复原优先级 → `vTaskDelete(NULL)`。调度器始终正常运行，既保持"全建完再调度"的语义，又允许 printf/ESP_LOG/malloc/vTaskDelay。
- 已 ninja 增量编译通过（G02.bin 已更新）。
