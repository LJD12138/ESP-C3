## 修复：Tmr Svc 上下文打印导致 newlib 锁重入 abort

- 现象：运行中出现 `abort() was called at PC 0x403810d3`，addr2line 指向 `lock_acquire_generic` @ `esp-idf-v5.5.2/components/newlib/src/locks.c:145`；前一行日志是 `uart: queue free spaces: 20`。
- 关键配置：`boardREPET_TIMER_CYCLE_TMIE = 10`（10ms），`boardDEBUG=1`（故 `boardWDGT_EN` 被 `#if(!boardDEBUG)` 关闭），`printREAL_TIME_OUT` 已定义故 `delay_value=0`（sMyPrint 非阻塞）。
- 根因：**`main/timer_task.c` 的 `v_timer_repet_callback`（运行在 FreeRTOS 软件定时器服务任务 Tmr Svc 上下文，每 10ms 一次）通过 `vSys_TickTimer()` 调用了 `sMyPrint` → `vsnprintf`**。`vsnprintf` 触碰 newlib stdout 流锁，与 PrintTask 侧打印重入同一把非递归锁 → `lock_acquire_generic` 断言 abort。
- 修复：
  1. `main/Sys/sys_task.c`：`vSys_TickTimer()` 内所有 `sMyPrint` 删除，改为置 `g_b_tick_state_log` 标志；新增 `v_sys_log_tick_state()`，由 `vSys_Task` 主循环（任务上下文）消费打印。`sys_task.h` 导出 `extern volatile bool g_b_tick_state_log`。
  2. `Hardware/Print/print_api.c/.h`：新增 `volatile u8 g_ucPrintLockout` 打印禁令计数；`c_print_start_check()` 前置守卫（`g_ucPrintLockout != 0` 或 `xPortInIsrContext()` 直接丢弃日志返回 -6）。
  3. `main/timer_task.c`：`v_timer_repet_callback` / `v_timer_signal_callback` 入口 `g_ucPrintLockout++`，出口 `g_ucPrintLockout--`（repet 用 `goto _repet_exit` 统一出口）。
  4. `Hardware/Print/print_api.c`：4 个打印函数的重复 `va_start` 改为 `va_copy/va_end`（栈安全）。
  5. `Hardware/Print/print_task.c`：`printTX_BUFF_SIZE` 384 → 1024（缓解高频日志积压）。
- 备注：`uart: queue free spaces: 20` 来源是 `Hardware/Print/print_iface.c:116` 的 `uart_driver_install(..., 20, &tUartQueue, 0)` —— UART 事件队列深度 20。
- 编译踩坑：`goto _repet_exit` 在 `#if(boardUPDATE)` 内，而 `boardUPDATE=0` 时标签无引用 → `-Werror=unused-label`。改为在升级分支内直接 `g_ucPrintLockout--; return;`，去掉 goto。

## 2026-10-13 ESP32-C3 启动崩溃排查（abort at newlib locks.c:145）

现象：`I (350) uart: queue free spaces: 20` 后立即 `abort() was called at PC 0x403810d3`。

结论（用本机 build/G02.elf + riscv32-esp-elf-addr2line 逐一解码）：
- PC=0x403810d3 = `lock_acquire_generic` @ newlib/src/locks.c:145，即 **递归型 newlib 锁（malloc 族 / stdout printf 族 / env / sinit / atexit，均指向 s_common_recursive_mutex）在 `xPortCanYield()==false` 时被获取** → IDF 主动 abort。
- 寄存器 dump 的 RA=0x40386676 是陷阱：它只是 `esp_system_abort` 里 `jal panic_abort` 的返回地址，恰好落在 esp_vApplicationTickHook 入口上，**与 tick hook 无关**（用户的 vApplicationTickHook 是空的）。
- RISC-V 移植下 `xPortCanYield()` 读中断阈值寄存器：**临界区（portENTER_CRITICAL / taskENTER_CRITICAL / taskDISABLE_INTERRUPTS）内一律视为 ISR 上下文**。
- 工程内主要嫌疑：`main/board_config.c` `vBoard_StartTask()` 在 `mainENTER_CRITICAL()`（=portENTER_CRITICAL）里遍历任务表，段内第 227/239 行有 `printf`，且各任务 init 里的 printf/malloc 族调用同样会触发。ESP_LOGI 用 vsnprintf 不递归锁所以 350ms 能打印。

修复方向：.printf/malloc/free 等递归锁 API 一律移出临界区与 ISR；日志改用环形缓存+任务延后发送。
